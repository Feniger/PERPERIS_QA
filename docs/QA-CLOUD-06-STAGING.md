# QA-CLOUD-06 — private staging on Cloud Run (milestone 4)

Status: rewritten on 2026-11-11 for the GitHub front end with no QA storage
(decision 4.2 in [QA-GITHUB-FRONTEND.md](QA-GITHUB-FRONTEND.md)). The earlier
Neon/PostgreSQL version of this guide and its database steps are gone.

Staging is the QA app on Cloud Run in QA's own Google project,
**`perperis-qa-staging`** (organisation lokalen.nu, billing account shared with
`kattens-pt`). It reads and writes issues in `krummb/kattens-pt` through the
"PERPERIS QA" GitHub App and nothing else of the training app.

- Address: **https://perperis-qa-staging-982639404002.europe-north1.run.app**
- Sign-in page is public; only emails on the member list get in.
- Production stays blocked by `runtime_guard.py`.

## What `infra/staging/setup.sh` creates (Cloud Shell, re-runnable)

- APIs: Cloud Run, Artifact Registry, IAM, Secret Manager, Identity Platform,
  API Keys and the keyless-sign-in services.
- Artifact Registry repository `perperis-qa` (keeps the 3 newest images).
- Service accounts:
  - `qa-runtime`: Cloud Run identity; may read its five secrets and view
    Identity Platform accounts (to end sessions of disabled/revoked users).
  - `qa-deployer`: used only by the deploy workflow; may deploy Cloud Run,
    push images, act as `qa-runtime` and see whether secrets have values.
- Keyless GitHub sign-in: pool `github`, provider `perperis-qa`, trusting only
  `Feniger/PERPERIS_QA`, `.github/workflows/deploy-staging.yml`, on `main`. No
  service-account key exists anywhere.
- Identity Platform with email/password sign-in and the staging host as the
  authorised domain; a browser API key limited to Identity Platform.
- Secrets (values never printed):

| Secret | Value |
|---|---|
| `perperis-qa-secret` | random, generated by the script (session signing) |
| `perperis-qa-webhook-secret` | random, generated by the script |
| `perperis-qa-web-api-key` | the browser API key (public by nature) |
| `perperis-qa-github-key` | **owner adds**: the GitHub App `.pem` file |
| `perperis-qa-members` | **owner adds**: e.g. `you@example.com=Admin:Your Name,creator@example.com=Admin:Their Name` (`:Name` optional; shown instead of the email) |

The script never replaces an existing secret value; rotate a secret by adding a
new version in the console and redeploying.

## Steps

1. **Setup** (done by Claude Code through the browser, owner's account): run
   `infra/staging/setup.sh` in Cloud Shell in `perperis-qa-staging`.
2. **Owner adds two secret values** in the console: Security > Secret Manager >
   `perperis-qa-github-key` > New version > upload the `.pem`; then
   `perperis-qa-members` > New version > paste the list. Never in chat or Git.
3. **Deploy** (owner approves each deploy): GitHub > Feniger/PERPERIS_QA >
   Actions > "Deploy staging" > Run workflow on `main`. The workflow checks that
   every secret has a value, builds and pushes the image, deploys and smoke
   tests `/api/auth/config`.
4. **First sign-in**: each member registers on the staging page with their
   listed email, verifies it from the email link, then signs in.
5. **Webhooks (optional, live updates)**: GitHub > Settings > Developer
   settings > GitHub Apps > PERPERIS QA > Webhook: active, URL
   `https://perperis-qa-staging-982639404002.europe-north1.run.app/api/github/webhook`,
   secret = the value of `perperis-qa-webhook-secret` (owner copies it from
   Secret Manager); subscribe to Issues, Issue comment, Pull request, Label,
   Milestone. Without webhooks QA still refreshes from GitHub every 60 seconds.

## Changing members

Add a new version of `perperis-qa-members` and run "Deploy staging" again
(Cloud Run reads `:latest` at start-up). Removing an email ends that person's
access on their next request after the new revision serves traffic.

## Rollback

Cloud Run keeps earlier revisions: Cloud Run > `perperis-qa-staging` >
Revisions > route 100% traffic to the previous one. Nothing else to roll back:
QA stores no data; tickets are GitHub issues.
